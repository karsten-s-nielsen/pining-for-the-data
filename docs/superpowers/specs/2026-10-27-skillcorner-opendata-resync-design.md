# SkillCorner Open Data re-sync — design

**Status:** approved — A/B rounds 1-3 (A r3 APPROVE, B r3 APPROVE, 0 open); owner approved 2026-10-27. Plan approved by A/B (r2) and the owner 2026-10-27; inline implementation.
**Date:** 2026-10-27
**Branch:** `feat/skillcorner-opendata-resync`
**ADR:** 0015 (new, this cycle)

## 1. Intent and why

The public SkillCorner Open Data loader fetches from the upstream `master` branch, so
the bytes it redistributes float to whatever upstream holds at fetch time. Ten of the
twenty live public entries now store older `dynamic_events` and `phases_of_play` than
upstream, because the loader skips every already-live id and so never re-fetches a
changed file. The live public store is therefore neither reproducible (no entry records
which upstream commit produced it) nor current (ten entries are stale).

This cycle pins the redistribution to one named upstream commit, records that commit in
every public opendata entry, brings the ten drifted entries' stored bytes up to the pin,
and verifies the result against the live store. The governing principle, approved by the
owner, is **pin, bump deliberately, upsert only**: the store stays on the pinned commit
until someone moves the pin; a re-sync updates and adds, and never deletes.

## 2. Goals

1. Pin the loader `scripts/upload_skillcorner_opendata.py` to one upstream commit, for
   the raw host, the Git-LFS media host, and the index fetch.
2. Record the pinned commit in each public opendata entry, in a new `source.revision`
   field.
3. Re-sync the ten drifted public entries so their stored artifact bytes equal the
   pinned commit, with a conditional-write (`If-Match`) path that aborts on a concurrent
   change and never deletes.
4. Stamp the pinned commit on all twenty public opendata entries.
5. Verify, against the live API and store, that each re-synced artifact's stored sha256
   equals the pinned upstream file's sha256, and that every entry carries the pin.

## 3. Non-goals

- No change to the owner/private SkillCorner tier, or to any other provider.
- No rebuild of the public `players.json`: every `_match.json` is byte-equal to the
  pin, so no player record changes. The re-sync touches match artifacts only.
- No automatic or scheduled re-sync; the run is a one-shot, gated ops step.
- No deletion of any live object or entry, and no re-tiering.
- No move of the pin beyond the commit named in this cycle.
- No change to the four-artifact layout, the artifact keys, or the public/owner tier
  split.

## 4. Anti-goals (a failure even if it runs)

- Floating the loader to `master` again, or to any moving ref.
- A write that clobbers a concurrent upstream change to the index or an artifact.
- A silent deletion of a live entry whose upstream file vanished.
- Recording a commit the stored bytes do not actually match.
- Any committed test fixture that carries a licensed provider id→entity tuple.

## 5. Constraints

- Python 3.12, ruff (line length 120), pyright basic, pytest. Pure transforms are
  unit-tested with injected callables; `main` performs the HTTP/S3 I/O only at the gated
  ops step.
- The repo is public: no local paths, third-party deep links, or dated correspondence in
  committed docs. Bare public MIT opendata match ids are allowed in committed code (the
  existing `scripts/verify_skillcorner_opendata_load.py` already lists ten), but never an
  id→entity tuple.
- `MatchEntry` (in `src/canonical/models.py`) is the schema source of truth; its JSON
  Schema is regenerated by `scripts/regenerate_schemas.py` and drift-tested in CI. A
  schema change updates the generated schema in the same commit.
- `updated_at` changes only when the entry changes (ADR 0013). Adding `source.revision`
  is an entry change, so every rewritten entry bumps `updated_at` once.
- One commit per cycle, on this feature branch, after the owner's explicit approval of
  that commit. The live write needs a separate explicit owner go.
- Pre-apply object VersionIds (or ETags) of every object the re-sync may change are
  recorded before the live write, for rollback (as in the Cycle A backfill).

## 6. The decided how

### 6.1 Pin the loader (`scripts/upload_skillcorner_opendata.py`)

Introduce one module constant for the pinned commit:

```python
UPSTREAM_COMMIT = "4340d274572876239c154c90bc507a9b3250a656"  # SkillCorner/opendata, 2026-09-14  # pragma: allowlist secret
```

Replace `master` with `UPSTREAM_COMMIT` in `RAW_BASE`, `MEDIA_BASE`, and the index fetch
(`http_get("matches.json")`). The media host accepts a commit SHA as the ref in
`media.githubusercontent.com/media/SkillCorner/opendata/<ref>/data`; the implementation
confirms this against the live host before relying on it (a documented risk, §9).

Moving the pin later is a one-line change to `UPSTREAM_COMMIT` plus a re-run under the
owner's go. The loader stays add-only for new ids; it gains no re-sync behaviour.

### 6.2 Record the commit (`source.revision`)

Add an optional field to `_SourceMeta` in `src/canonical/models.py`:

```python
revision: str | None = Field(
    default=None,
    pattern=r"^[0-9a-f]{40}$",
    description="Upstream VCS commit the redistributed bytes were fetched from (git SHA-1).",
)
```

`upload_game` gains a `source_revision: str | None = None` parameter, forwarded into the
`source` sub-object alongside `name`/`url`/`licence`. `revision` rides the existing
`if source_name:` gate (`src/mock_api/upload.py:177`): the `source` object is built only
when `source_name` is set, so `revision` is written only then. Opendata always passes
`source_name` (`"SkillCorner Open Data"`), so the field is always written for this
provider. The loader and the re-sync both pass `UPSTREAM_COMMIT`. The `provenance` string
stays `"redistributed"`, so every existing consumer and test that reads
`provenance == "redistributed"` is unaffected (Hyrum's law).

`_SourceMeta` is shared by `MatchEntry` and `PlayerRecord`, so adding `revision` changes
both `matches.schema.json` and `players.schema.json`. Regenerate both in the same commit
(`scripts/regenerate_schemas.py`); CI runs the full suite (`uv run pytest`,
`testpaths = ["src/tests"]`), so `test_schemas.py` drift-tests the result. Player records
never set `revision`, so the player data is unaffected.

### 6.3 The re-sync path (`scripts/resync_skillcorner_opendata.py`, new)

A separate single-purpose script, matching the repo's per-provider load/verify
convention. It reuses `stage_match`, `fetch_resolved`, `opendata_files`, `match_info`,
and the entry-build/validate in `upload_game` (never duplicating `MatchEntry`
assembly). Dry-run by default; `--apply` writes.

For each target id (the full set is all twenty public opendata ids; the ten drifted ids
are the ones whose artifacts actually change — §6.5):

1. Read the live entry from `skillcorner/matches.json` and the current ETag of each of
   its artifact objects.
2. Re-stage all four artifacts from the pinned commit. The three small roles (`match`,
   `dynamic_events`, `phases_of_play`) give their real bytes. `tracking_extrapolated` is read as
   its Git-LFS pointer, whose `oid` IS the content sha256, so the drift check uses the pointer
   `oid`/`size` without the ~90 MB blob download (ADR 0015). `tracking` is never re-PUT, so only
   its content identity is needed here; the post-apply verify (§6.6 item 4) is what downloads and
   hashes the stored tracking bytes.
3. Hash each staged artifact. Compare each to the stored `artifact_meta[key].sha256`.
   Only `dynamic_events` and `phases_of_play` may be re-PUT. A `dynamic_events` or
   `phases_of_play` whose fresh sha256 differs is re-PUT, conditional on that object's
   ETag (`PutObject` with `If-Match`). When the entry has no stored `artifact_meta` for
   such a key, re-PUT that artifact (fallback). A differing `match` or
   `tracking_extrapolated` is an **unexpected** drift: it breaks the players.json waiver
   (§3) and would need a players rebuild that is out of scope, so the run reports that
   match and stops it (no re-PUT, no index write). It is reported, not silently re-sent.
4. Carry the live entry unchanged except for three fields: replace `artifact_meta` for the
   re-PUT roles, add `source.revision = UPSTREAM_COMMIT`, and let `updated_at` bump (ADR
   0013, because the entry changed). Every other field (`home`, `away`, `date`,
   `provenance`, `source.name`/`url`/`licence`, the competition/season fields,
   `visibility`) is copied verbatim from the live entry — never rebuilt from upstream,
   because the original ten entries were not written by this loader and an upstream rebuild
   could change them. The dry-run prints a per-entry field diff; the apply refuses the
   write if any field other than `artifact_meta`, `source.revision` and `updated_at` would
   change. Validate the assembled entry, then rewrite `skillcorner/matches.json`
   conditional on the index object's current ETag (`If-Match`).

   **The `source.name` precondition.** `source.revision` lives in the `source` object,
   and the model requires `source.name` (`models.py:36`). Stamping `revision` on an entry
   that has no `source` object would have to create `source.name`, which the three-field
   guard above then refuses — a deadlock. Live read on 2026-10-27 confirmed all twenty
   public opendata entries already carry `source` with `source.name`
   (`provenance = "redistributed"`, a four-key `artifact_meta` each), so the deadlock
   cannot arise for this data. The re-sync still handles it: an entry with no `source`
   object is reported-and-stopped (no write), never half-stamped. §6.8 tests this.

A `412 Precondition Failed` on any conditional write means the object changed under the
run. The run aborts that one match, reports it, and continues with the others; it writes
nothing further for the aborted match. No object or entry is ever deleted. An artifact
file that vanished upstream (fetch 404) is reported and the live object and entry are
kept — reported, not an error that stops the run. At this pin no file is missing (the
pinned tree holds all 80 artifacts), so a 404 cannot occur here; the rule stands for a
future pin.

**Partial-write state and recovery.** S3 has no multi-object transaction. The re-sync
PUTs the changed artifact(s) first and the index entry last. A failure after an artifact
PUT and before the index write leaves the new bytes in S3 under the old `artifact_meta`
sha256 — the inconsistent state the earlier `scripts/backfill_skillcorner_opendata_lfs.py`
(docstring lines 10-13) names, where a consumer that validates bytes against
`artifact_meta` would reject the object. Recovery is to re-run the re-sync: it is
convergent — it re-stages, finds the object's stored `artifact_meta` still mismatched,
re-PUTs, and rewrites the entry. The verify (§6.6) asserts the stored bytes equal
`artifact_meta`, so a partial write is detected, not passed over. Pre-apply VersionIds
(§7) allow a rollback.

### 6.4 Why conditional writes

`skillcorner/matches.json` is one shared index rewritten read-modify-write per match, so
a concurrent write (another ops run, a future CI apply) could lose an update. `If-Match`
on the index write turns a lost update into a visible `412` that the operator re-runs.
`If-Match` on each artifact PUT gives the same guarantee for the object bytes. This is
the "IfMatch re-sync path" of the approved scope.

### 6.5 Scope of change across the twenty entries

All twenty entries are rewritten to add `source.revision`; each bumps `updated_at` once.
An artifact object is re-PUT only where its fresh sha256 differs from the stored one. By
the read-only drift audit, that is `dynamic_events` and `phases_of_play` for these ten
ids:

```
1886347 1899585 1925299 1953632 1996435 2006229 2011166 2013725 2015213 2017461
```

`match` and `tracking_extrapolated` are byte-equal to the pin for all twenty, so neither
is re-PUT. The other ten public ids (the set in `verify_skillcorner_opendata_load.py`)
are byte-equal to the pin on all four artifacts; they get only the `source.revision`
stamp and the `updated_at` bump.

### 6.6 Verify afterwards (`scripts/verify_skillcorner_opendata_resync.py`, new, or an
extension of the existing opendata verify)

Against the live API and store, assert, for all twenty entries and all eighty artifacts
(not only the re-sent ones — stamping an entry whose bytes do not match the pin is the
exact failure §4 forbids):

1. The public listing still has twenty entries and every id is present (the existing
   `verify_listing`).
2. Every public opendata entry carries `source.revision == UPSTREAM_COMMIT`.
3. For the three non-LFS roles (`match`, `dynamic_events`, `phases_of_play`) of every
   entry: fetch the stored object through the API, hash it, and assert its sha256 **and**
   size equal both (a) the pinned upstream file (fetched fresh from the pinned commit) and
   (b) the entry's `artifact_meta[key]`. Equality with (a) proves the store matches the
   pin; equality with (b) proves `artifact_meta` matches the stored bytes, so a partial
   write (§6.3) is caught. These objects are small (CSV and JSON), so fetching all sixty
   is cheap.
4. For `tracking_extrapolated` (LFS) of every entry: download the stored object, hash it,
   and assert its sha256 **and** size equal both (a) the pinned upstream Git-LFS pointer's
   `oid` and `size` (read from the raw host) and (b) the entry's `artifact_meta[tracking]`.
   This proves the stored tracking bytes equal the pin from the bytes themselves, not from
   `artifact_meta` alone — the same bar as `verify_match_index_fields.py --full-hash`
   (ADR 0013). It costs one full download per file (~90 MB × 20, a one-time post-apply
   verify run by the operator), and that cost is accepted so no stored artifact is proven
   by assumption. Nothing in this item is left to the `artifact_meta` value as a proxy.
5. The existing servability and not-a-pointer checks still pass.

This reuses `verify_match_index_fields.py --full-hash` for the stored-vs-`artifact_meta`
idea and the LFS helpers (`is_lfs_pointer`, `parse_lfs_pointer`, `verify_blob`) for the
pointer `oid`.

The pure checks take injected callables and are unit-tested; `main` wires them to the
live API and the pinned upstream. No licensed id→entity tuple is committed.

### 6.8 Tests for the re-sync core

The anti-goals in §4 are the behaviours most in need of a red step. Each gets a unit test
with injected fakes (a fake S3 that raises a `412`/`404` on command and records PUTs, and
a fake fetch returning staged bytes), so no behaviour ships untested:

- `test_resync_skips_put_when_sha_matches` — a `dynamic_events` whose fresh sha256 equals
  the stored `artifact_meta` sha256 is **not** re-PUT (the no-diff side of the gate).
- `test_resync_puts_when_sha_differs` — a `dynamic_events` whose fresh sha256 differs is
  re-PUT once, with `If-Match` set to the stored ETag (the diff side).
- `test_resync_412_aborts_only_that_match` — a `412` on an artifact or index write aborts
  that one match, writes nothing further for it, and the loop continues with the rest.
- `test_resync_unexpected_match_or_tracking_drift_reports_and_stops` — a differing `match`
  or `tracking_extrapolated` is reported and that match is stopped, with no re-PUT.
- `test_resync_missing_artifact_meta_fallback_puts` — an entry with no stored
  `artifact_meta` for a re-syncable role re-PUTs that artifact.
- `test_resync_vanished_file_reports_and_keeps` — a `404` on an upstream fetch reports the
  file and keeps the live object and entry (no delete), and the run does not stop.
- `test_resync_carries_entry_fields` — only `artifact_meta`, `source.revision` and
  `updated_at` change; a would-be change to any other field refuses the write.
- `test_resync_entry_without_source_reports_and_stops` — an entry with no `source` object
  is reported and stopped, with no write (the `source.name` precondition, §6.3 step 4).
- `test_verify_tracking_hashed_from_stored_bytes` — the verify downloads and hashes the
  stored `tracking_extrapolated` object and fails when its sha256 differs from the pin,
  proving tracking is checked from bytes, not from `artifact_meta` alone (§6.6 item 4).
- `test_source_revision_in_schema` — the regenerated `matches.schema.json` and
  `players.schema.json` carry `revision` (drift check in `test_schemas.py`).

## 7. Rollout (each gate needs the owner's explicit go)

1. Commit gate: the owner approves the one commit. It holds everything for the cycle, as
   past cycles did (`7483ee8`, `44930cf`): the code, the regenerated `matches.schema.json`
   and `players.schema.json`, ADR 0015 and its README row, the spec and the plan with the
   review dispositions, the tests, the **version bump** (`pyproject.toml` and `uv.lock`),
   the `CHANGELOG.md` entry, and the `docs/api-reference.md` update to the `source`
   object shape (the `{name, url, licence}` description near line 159 gains `revision`).
   The version bump is in this commit, not a second post-merge commit. Branch
   `feat/skillcorner-opendata-resync`, PR, CI green.
2. Pre-apply gate: the data bucket has versioning on, so record the **VersionId** (not the
   ETag) of `skillcorner/matches.json` and of every artifact object the re-sync may
   change; a VersionId rolls back, an ETag does not. The `If-Match` precondition still
   uses the ETag — that is concurrency control, separate from rollback. Run the re-sync
   dry-run and read its per-entry field diff.
3. Live-write gate: the owner approves `--apply`. Run the re-sync against the live
   bucket. A `412` on any match aborts that match and is reported.
4. Verify: run the content-identity verify (§6.6) against the live API and store; it must
   pass.
5. Release gate: the owner approves the tag and GitHub Release (the version bump already
   landed in the cycle commit at step 1).

A merge to `main` touching `terraform/**` triggers a live `terraform apply`; this cycle
changes no `terraform/**` file, so the merge itself makes no infra change. The re-sync is
an S3 data write, run from an operator profile, gated separately.

## 9. Risks

- The media (LFS) host accepting a commit SHA as the ref is **confirmed** (reviewer B:
  the media host serves the LFS blob by commit SHA, HTTP 206). No longer an open risk; the
  implementation still asserts a 206 before relying on it.
- S3 `PutObject` `If-Match` support is assumed; the implementation confirms it against the
  live bucket (a conditional PUT returns `412` on a stale ETag) before the live run, the
  same confirm-against-live discipline as the media check.
- A concurrent writer during the live re-sync raises `412`; handled by abort-and-report,
  not data loss.
- A crash between an artifact PUT and the index write leaves a partial state; recovery is
  a convergent re-run and the verify detects it (§6.3, §6.6).
- Adding `source.revision` to all twenty entries bumps twenty `updated_at` values once;
  this is a real metadata change and is expected, not drift.
